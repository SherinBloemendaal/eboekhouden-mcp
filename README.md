# EB MCP

A menu-bar app (macOS, and Windows from the same code) that signs in to e-Boekhouden and offers its internal API to AI clients (Claude, Cursor) as a local MCP server: read-only, unless you turn writing on for an account.

- Product spec and design boards: `~/projects/eb-mcp-design` (`SPEC.md`, `BOARDS.md`, the EB MCP canvas).
- Roadmap and what is left: [docs/ROADMAP.md](docs/ROADMAP.md).

## How it works

- **Accounts** (`src-tauri/src/accounts.rs`): label, username or `op://` item, administration and which store holds the password. Never a password in the app's files. There is no default account: with more than one, every tool call must name its account, so an AI client never reads the wrong books.
- **Credentials** (`creds.rs`): 1Password through the `op` CLI, or the system store (Keychain with Touch ID, Credential Manager with Windows Hello), read only at sign-in.
- **Sign-in as the browser does it** (`signin.rs`, `ebapi.rs`): EB MCP fetches e-Boekhouden's login page (`bh/inloggen.asp`) and posts its form with the username and password from 1Password or the Keychain. The answer sets the `auth-token` cookie that e-Boekhouden's API reads; EB MCP then checks the session with `POST auth`, as their app does at startup. Token and cookies stay in memory only. Two-step verification on this form is not built yet: the sign-in stops and its diagnosis names the page's fields. (0.1.9 to 0.1.11 used the `auth/login` of their new app, which answers 500 for ordinary accounts.)
- **API** (`ebapi.rs`): calls under `/v1/api/` with the session's cookies, 60 a minute and 2 at a time, and a growing pause after errors. Reads are GETs; a change is a POST, PUT or DELETE, never retried (a quote with lines, or a template with its layout, takes several).
- **MCP** (`mcp.rs`, `tools.rs`): Streamable HTTP on `http://127.0.0.1:47821/mcp`, behind a bearer token, loopback Host only and no browser `Origin`. 179 tools: the 57 of `tools.rs` and 122 that live per part in `tools/*.rs`, each part on its own router. `inloggen` signs an account in the way the app's own button does (the credentials come from 1Password or the Keychain inside EB MCP and never reach the client), waits for the outcome and never retries. The generic `get` reads only the 300 plain paths in `data/get-paths.txt` (`scripts/gen_get_paths.py`), and refuses an action word in any segment: some of e-Boekhouden's GETs change things (paying a btw return, handing an administration over), and those stay out.
- **Arguments as clients send them** (`lenient.rs`): a field that may be left out names one plain type in every tool's schema (`"type": "string"`, not `["string", "null"]`, which Claude read as untyped), and before a tool reads its arguments a number sent for a text field becomes that text and a plain number sent as text becomes that number. So an account code like 1810 works whether it arrives as `1810` or `"1810"`.
- **Writing** (`write.rs`, `approvals.rs`, `hub.rs`): off for every account until the user turns it on (Accounts, per account), with a level per kind of change: boeken en wijzigen (adding and changing, which can be put right), verwijderen (deleting, which cannot), versturen (mail, Peppol, the incassobestand, a message or assignment to the accountant) and ingrijpend (crediting, invoicing or booking in bulk, writing off, the beginbalans, company details, processing a btw-aangifte, and a change that moves where money or mail goes). Each is off, with approval, or without; versturen and ingrijpend never go without approval. Three presets set all four at once: Alleen lezen, Alles met akkoord, and Vrij boeken (adding and changing at once, the rest with approval). A tool whose kind is off refuses and says which kind; `status` names the four levels per account. An account file from before 0.6.0 held one setting, which is read as the matching preset. With approval a tool's change goes into a queue (the Akkoord page) and the tool answers its client at once that it waits; the change goes to e-Boekhouden in the background only after Goedkeuren, one by one or all the listed ones together, and the `akkoord_status` tool tells the client what came of it. A client can take its own waiting request back with `akkoord_intrekken` (wrong amount, asked twice, no longer needed): it leaves the queue, nothing goes to e-Boekhouden, and the history shows it as Ingetrokken with the client's name and reason. Once approved, a change is no longer the client's to stop. What waits shows as a badge in the sidebar, a banner, a toast, a count next to the menu-bar icon and a system notification; it lapses when EB MCP stops. Every proposal, also a change made without approval, stays in a history with its request body and outcome (`approvals.json.gz`, exportable as `eb-mcp-akkoord-*.jsonl.gz`); crediting, invoicing subscriptions, mailing an invoice and changing where an e-mail template sends its mail always ask, and deleting asks unless the user set verwijderen to go without. The tools book and edit mutaties of all seven kinds, upload files to the digitaal archief and link them to a mutatie, make, edit, credit, delete and e-mail invoices (and fetch one as a PDF into Downloads), make, edit and delete subscriptions and e-mail templates, and delete a mutatie or an archive file. An edit of an invoice or subscription can add, change and remove single lines by their id (`regels_toevoegen`, `regels_wijzigen`, `regels_verwijderen`): the other lines are not sent, so they keep their id, artikel, eenheid and place; `regels` still replaces them all. A subscription line may have aantal 0. Deleting a mutatie says that a correcting entry is the better bookkeeping, and deleting a file that is still linked comes with a warning; both follow the account's level for verwijderen. Relaties can be added, edited and deleted; a change of IBAN, BIC or an e-mail address always asks. Quotes can be made, edited, deleted and fetched as a PDF. Templates: e-mail and dunning templates as text, and the layout of invoice and quote templates through the API of e-Boekhouden's own template editor (`editor.e-boekhouden.nl`): a tool reads the layout document, and a changed one is saved after the user has seen what changes per element. Templates that are an uploaded RTF are left alone. The request shapes were taken from e-Boekhouden's own web app and checked against a test administration (2026-11-11); mailing an invoice is the one that was built from the web form's code and first sent after the release. "Facturen maken" for subscriptions runs on e-Boekhouden's SignalR hub over a WebSocket, as their page does.
- **The parts in `tools/`** (built from e-Boekhouden's public web app code; not yet tried against e-Boekhouden itself, see the notes per part before relying on one): Mijn gegevens (company details and invoice address, always with approval; e-Boekhouden's own invoices as PDF), uren (hours, projects, activities, overviews, invoices from hours, settings), producten en diensten and standaard facturen, grootboekrekeningen, rekeninggroepen and kostenplaatsen (also on a mutatie line), open posten (reminders and dunning, writing off; postponing is not possible, their page makes no API call for it), berichten and controleopdrachten, automatische importregels, vaste activa and depreciation, the beginbalans, btw-aangifte, ICP and suppletie (reading, processing into the books, correcting), following up quotes (mail, invoice from a quote, progress, agenda), the incasso file, Peppol, mailing and printing invoices in bulk, unlinking an archive file, and the list of e-mail template codes. **Never built:** filing or paying a btw return, an ICP or a suppletie, changing the incasso IBAN or the licence, cancelling. What EB MCP can do is look up the iDEAL link of a sent btw return (`btwaangifte_betaallink`) for the user to open themselves: asking e-Boekhouden for a new link starts a payment there and always needs approval, EB MCP never opens the link, and the link is masked in the request log, the approval history on disk and the exports. A test in `tools/btw_aangifte` fails when that module can reach a filing path. A change that waited for approval is checked again before it goes out where the facts can move meanwhile (the incasso list, hours to invoice, company details). Money is rounded to cents as e-Boekhouden's forms do (`write::round_cents`). An invoice mail is sent with the text e-Boekhouden itself fills in for that invoice (`factuur/maildata`), shown in the approval as it will be sent.
- **Sessions** (`state.rs`, `signin.rs`, `settings.rs`): a session lives in memory only. By default EB MCP forgets one that no AI client used for the idle time (15 minutes to 4 hours, Instellingen). With **Blijf ingelogd** on (off by default) there is no idle sign-out; instead EB MCP asks e-Boekhouden every five minutes whether each session still stands (`POST auth`, the check its own app makes at startup) and keeps cookies the answer renews. A session e-Boekhouden ended anyway shows as expired, and only that check lands in Verzoeken; EB MCP does not sign in again by itself, since that would put up a Touch ID or 1Password prompt out of nowhere. How long e-Boekhouden keeps a session that is asked after this way is not published and was not measured. **Alles inloggen** (Accounts) starts a sign-in for every account without a session; at most four talk to e-Boekhouden at once, the rest wait for their turn, and usernames and passwords are read one account at a time so 1Password or the system store asks one question at a time.
- **Bank lines** (`bankregels`, `mutatie_toevoegen`): `bankregels` lists the imported statement lines that are not booked yet. `mutatie_toevoegen` with `bankregel_id` books one, for every kind of mutatie, an invoice payment too: it sends the line's id as `importId` in the same `POST mutatie` as e-Boekhouden's own form, and the line leaves the unprocessed list. That request was captured from a real booking on 2026-11-11; the payment form sends the same field (read from the web app's code, not yet seen live). The tool reads the line first, refuses an id that is not among the unprocessed lines (so nothing is booked twice), shows the line in the proposal and says where the booking's account, direction or total differs from it. A mutatie booked without `bankregel_id` leaves the bank line open. Not built: writing several lines off to one account at once (`import/bulk/wegboeken`).
- **Request log and Dashboard** (`reqlog.rs`, `logstore.rs`): the last 1000 calls, MCP calls linked to the e-Boekhouden calls they caused, secrets masked, each with the app version that made it. Log and statistics are kept in `request-log.json.gz` in the app's config folder (user-only, written atomically), so they survive restarts and updates until Leegmaken. Verzoeken can export everything to one `eb-mcp-debug-*.jsonl.gz` in Downloads for debugging.
- **Koppelen** (`connect.rs`, `bridge/`): writes the entry into Claude Desktop's or Cursor's config after a confirm, with a backup and a read-back. Claude Desktop starts only stdio servers, so it gets `eb-mcp-bridge`, a small sidecar that forwards to the HTTP server. An MCP session may sit unused for a day (rmcp's own default is five minutes, after which the first call after a pause answered 404). When EB MCP no longer knows a session at all, after a restart for an update for one, the bridge starts a new one with the client's own `initialize` and sends the request again, so Claude Desktop does not have to be restarted.
- **Liquid Glass** (`glass.rs`, `src/lib/glass.ts`): on macOS 26 the sidebar card of the main window is real system glass. The page reports where the card is (`set_glass`), and the app puts an `NSGlassEffectView` there, under the transparent webview; the window then paints an opaque background and drops the whole-window material of `tauri.conf.json`. The card turns clear only after the app has answered that the glass is there. macOS 13 to 15, Windows and the menu-bar panel keep the material and the CSS glass they had.
  To turn native glass off (back to the CSS glass, for a window that misbehaves), then quit and open EB MCP again: `defaults write dev.sherin.ebmcp NativeGlass -bool false` (undo with `defaults delete dev.sherin.ebmcp NativeGlass`), or for one run `open --env EB_MCP_NATIVE_GLASS=0 -a "EB MCP"`.
- **Menu bar** (macOS, `build_menu` in `lib.rs`): EB MCP, Archief (Account toevoegen, Alles inloggen, Alles uitloggen, Open e-Boekhouden), Wijzig, Weergave (the five pages on Cmd+1 to Cmd+5, the sidebar, full screen), Venster and Help. Every item does what a button in the app does; `menu_action` maps an item's id to its action and a test keeps the pages in the sidebar's order.
- **Updates** (`updates.rs`, ported from Tresso): Sparkle on macOS, Tauri's updater on Windows, signed releases from `.github/workflows/release.yml`.

## Develop

```bash
npm install
npm run tauri dev
```

`tauri dev` first fetches Sparkle (pinned, SHA-256 checked) and builds the bridge. The MCP token lives in a file in the app's config folder that only the user can read: `token.json` in release builds, `dev-token.json` in debug builds. It is not in the Keychain, because the ad-hoc signed app would otherwise ask for the Keychain password at every start after each update, and the bridge reads the same file without a prompt. A release that finds a token from an older version in the Keychain moves it to the file once.

## Checks

Run them one at a time:

```bash
npm run typecheck
npm test
cd src-tauri && cargo fmt --check && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace
```

Agents never sign in to e-Boekhouden or enter passwords. Tests use mocked pages and answers; the real sign-in is tested by hand.

## Releases

A tag `v1.2.3` builds macOS (universal) and Windows and publishes a GitHub release with `appcast.xml` and `latest.json`. The repository needs:

- variables `SPARKLE_PUBLIC_KEY` and `TAURI_UPDATER_PUBKEY`;
- secrets `SPARKLE_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY` and `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`.

Keep the private keys in 1Password and never rotate them: installed apps trust only these keys.
